# CLAUDE.md — sim (market data generator + FIX counterparty)

Everything fake lives here so nothing fake lives anywhere else. The demo is fully self-contained: no real connectivity.

Code location: sim's Rust binary is the `sim` crate in the `delta-one/` Cargo workspace (ADR-007); this directory holds scenarios (`scenarios/`), golden outputs (`golden/`, containing four `.jsonl` files of post-trade Avro records decoded to JSON — `posttrade.{trades,crosses,allocations,orders.audit}.jsonl` — one object per line; regenerate with `UPDATE_GOLDEN=1 cargo test -p d1 --test golden_posttrade -- --ignored`) and these rules.

## Components

1. **Market data generator** (Rust binary, shares `d1` message types): publishes ticks for the demo universe. Modes: `replay` — deterministic scripted scenarios (the demo runs on these), `emit-ticks` — expands a scenario timeline into a plain-text tick file (`--scenario <yaml> --out <path> [--script-out <path>]`; one `d1_core::FeedTick` per line, six whitespace-separated integers) that `d1 --feed-ticks` replays into its feed ring, `random-walk` — correlated GBM with configurable vol/correlation for soak testing, `burst` — throughput stress for latency measurement. Feeds Delta One over the same in-process/UDP path the real feed handler will use — the hot-path measurement must include the ingest boundary.
2. **FIX acceptor** (QuickFIX-based): accepts FIX 4.4 sessions from `d1-gateway-fix`, fills orders per a configurable fill model (immediate / partial / delayed / reject rate), emits ExecutionReports. This stands in for a broker/EMS; venue-dialect adapters (EMSX, TSOX, FXAll) come only when real specs and entitlements exist.
3. **Scenario runner:** YAML scenarios that script market moves + EXO book events for the showcase (e.g., "underlying gaps down through autocall barrier → EXO delta jumps → cross vs D1 tracker flow → residual executes externally → post-trade lands in Kafka → UI shows lineage"). The demo story lives here as code, not in someone's head. Feed-bearing actions understood today are `quote`, `gap` and `dividend`; `action: exo_book_event`, `action: tracker_flow` and every `expect:` entry are harness checkpoints with no tick (ADR-014 §10): `emit-ticks --script-out` writes them as one line each (`<at_ms> book_event <book>`, `<at_ms> tracker_flow <book> <instrument> <target_e2> <band_e2>`, `<at_ms> expect <kind>`) for `crates/d1/tests/storyline.rs`, and `scenario::load` rejects an unknown `expect` kind or a `tracker_flow` missing a field. `fill_model:` is parsed, not applied (the acceptor takes `--fill-model`). `replay` and `emit-ticks` both expand the timeline via `emit::expand`; a `dividend` is one ex-div tick (all three prices dropped by the amount, `div_per_share_e9` set), which `replay` ingests and credits exactly as `run_core` does.

## Rules

- Deterministic by default: every scenario has a seed; two runs of the same scenario produce byte-identical Kafka output (this is also the end-to-end regression test: `just demo` diffs the post-trade stream against a golden file).
- The simulator may be sloppy about latency but never about protocol correctness: FIX session behavior (sequence numbers, resend, logon/logout) must be spec-correct, because Delta One's session handling is being tested against it.
- No sim code may be imported by production crates/packages; dependency direction is sim → protocol only. This is the target *wire-format* rule (Protobuf/Avro on NATS/Kafka). Documented carve-out (P1.M1, ADR-004): `d1-core` stays Protobuf-free, so `sim` depends on `d1-core`'s public `FeedTick` struct to drive `MarketData::ingest` in-process — the dependency runs sim → d1-core, never the reverse, and no production crate imports sim. The M1 feed boundary is a plain function call (`MarketData::ingest`), not a queue or socket; M2 drops an SPSC ring in front of it once a real consumer thread exists. **The `emit-ticks` transport does not weaken this rule**: `d1` does not import `sim` and `sim` does not import `d1`; the coupling is a text file that `sim` writes and `d1` parses at startup, one direction, with no shared code and no new dependency in either crate. (This is also why the former "give `sim` a `lib.rs`" suggestion in `docs/PONYTAIL-DEBT.md` was withdrawn rather than implemented — a lib target would still leave `d1` unable to depend on it under this rule.)
