**P1.M5 markers (tracker analytics):** benchmark composition is a PRICE return while book NAV is a TOTAL return — constituent dividends land entirely in tracking difference, appearing as an ~8bps active-return spike on the ex-dividend sample, which in a short window dominates the variance; end-of-session Kafka cadence is a process-boundary limitation (a real deployment triggers on EOD, this process never sees it); `publish_interval_s` is parsed and range-validated but not wired (publishes on every sample, not separately cadenced); second corporate-action transport type needed (currently only `FeedTick.div_per_share_e9`); integration-coverage gap: `DIVIDEND_AT_NS` (9s) never fires during golden run, cannot be closed without rewriting all four golden fixtures.

**P1 exit-criteria markers (tick-to-trade bench, `feat/d1-t2t-bench`):** four shortcuts sit behind the Phase 1 exit criterion now recorded as met in `docs/ROADMAP.md`.

- **Unpinned cores — ADR-004 §5 half-unmet.** §5 asks for HDR histograms "on release builds with **pinned cores**". The release-build half holds (`bench` profile inherits `release`); the pinning half does not. macOS/Apple Silicon does not honour thread-to-core affinity — the Mach `thread_policy_set` affinity tag is a hint Apple Silicon ignores — so a `core_affinity` call would compile, run, and silently do nothing, which is worse than not pinning, because the report would claim a property it does not have. No dependency was added; `benches/tick_to_trade.rs` prints an explicit UNPINNED note instead. *Upgrade:* a Linux CI runner, where affinity is real, is the only path that closes this.
- **Composed-path, not live-loop causal.** The reported T2T number assembles the four ADR-004 §1 stages in one timed closure in `run_core`'s live call order; it is not a timestamp taken across a real tick flowing through the running process. The sequence is target-triggered, which ADR-004 §1's own parenthetical ("the next tick *or an immediate synthetic evaluation event*") covers, so this is a measurement-fidelity gap, not an ADR violation. Read this precisely: it does **not** mean a causal path exists and merely went uninstrumented. There is no tick-triggered evaluation arm in `run_core` at all — feed ingest and target-driven netting sit in two separate `if let Ok(…)` arms of the same poll loop — so the bench composes a sequence the process never today executes end to end from a single stimulus. *Upgrade:* a live measurement needs only a tick-triggered evaluation arm in `run_core` plus ingress/egress timestamps — notably **not** new state, because `NettingSession::targets` (`crates/d1/src/cycle.rs:117`) already *is* the persistent desired-position table ADR-004 §1 describes.
- **The measured path allocates and does I/O.** `NettingSession::on_target` performs ~6 heap allocations per cycle (`crates/d1/src/cycle.rs:197`, `214`, `230`, `250`, `259`, `307`, `316`) plus an unconditional `println!` on every parent-order mint (`:320`) — all inside the window ADR-004 §1 budgets. This sits in tension with `delta-one/CLAUDE.md`'s hot-path contract (rule #1 no heap allocation, rule #3 no syscalls/I/O/logging "on any code reachable from the hot path") while `cycle.rs:6-9`'s own module doc declares the module off the benchmarked hot path. Both cannot hold: `docs/ARCHITECTURE.md` budgets "Netting evaluation (incremental) ≤ 10 µs" as a T2T stage and `run_core` reaches it through `on_target`. The four isolated stage benches could never expose this, because they only ever covered the alloc-free crates (`d1-core`, `d1-netting`) — the allocating orchestration layer *between* them was on no measured path. Latency consequence today is bounded (measured p50 is roughly an order of magnitude under budget) but it is headroom being spent, and the `println!` alone drives the run-to-run p99 variance. There is also a second-order **operational** consequence: that `println!` fires once per netting cycle and embeds `ClOrdId`'s derived `Debug` over `[u8; 20]` (`crates/d1-core/src/ids.rs:15-16`), rendering ~200 bytes as `ClOrdId([48, 48, 48, …])`. Across a bench run's ~10⁶ cycles that is **~245 MB of stdout per `just bench` run, measured** — which buries the ADR-004 §5 report lines it is supposed to deliver and would make any CI job capturing that output produce a quarter-gigabyte artefact. Until the `println!` moves to a telemetry ring, run `just bench` with stdout redirected. *Upgrade:* **owned by P4.M2** (rho transfer — the first milestone that adds work through `cycle.rs`'s cross-booking path, since `on_transfer` books a directed cross through the same `book_cross` helper netting-derived crosses use; P4.M3's proposal execution then rides the same path). Decide which document is wrong: either make `cycle.rs` alloc-free and route its logging through a telemetry ring (rule #3's prescribed shape), or amend `delta-one/CLAUDE.md`'s hot-path contract to state that netting *orchestration* is explicitly outside it and adjust `docs/ARCHITECTURE.md`'s per-stage row accordingly. The same decision covers `run_core`'s ingest-arm `println!` (`crates/d1/src/lib.rs:448-453`), which is the same class of demo-grade stdout logging and sits just outside the benched window.
- **`d1` scenario feed — transport half DELIVERED** (`chore/ponytail-d1-scenario`). `crates/sim` gained `--mode emit-ticks`, expanding a scenario timeline into a plain-text tick file (six whitespace-separated integers per line: `instrument_id bid_px_e9 ask_px_e9 last_px_e9 exch_ts_ns div_per_share_e9`, one `d1_core::FeedTick` each); `crates/d1` gained `--feed-ticks <path>`, parsing it at startup (`crates/d1/src/tickfile.rs`) and replaying it into the existing feed ring in real time (`feed::run_tick_file_producer`, absolute per-tick deadline so pacing error cannot accumulate). Opt-in — absent the flag the synthetic walk is untouched, which is what keeps `sim/golden/*.jsonl` and `benches/tick_to_trade.rs` byte-identical and passing. **This ledger's own former suggested fix was half-wrong and is withdrawn:** "give `sim` a lib target" would not have worked, because `sim/CLAUDE.md` forbids any production crate importing `sim`, so a `lib.rs` still leaves `d1` unable to depend on it. Only the transport half was ever open; what shipped is a text file — one direction, at startup, **zero new dependencies in either crate**. Four residuals, all P2.M4: (1) **no tracker analytics on this path** — `d1.toml`'s `[tracker].sampling_interval_s = 60` against a timeline whose `exch_ts_ns` tops out at 9e9 means zero sampling-boundary crossings, so the demo's headline analytic does not appear (`run_core` logs "no end-of-session tracker record ... window has 0 observation(s)" — graceful, but a reviewer will look for the analytic and not find it); setting `d1.toml` to `1` would break `config.rs::parses_real_d1_toml` and redefine the demo-time-day semantic, i.e. a tracker-output change, not a transport change. (2) **14 of 15 universe instruments are never quoted** by `tracker-flow.yaml` and therefore hold `run_core`'s t=0 prime of 150.00 for the whole session, so internal crosses on them book at that prime rather than a scenario price — surfaced by `tickfile::report_coverage`'s startup warning (the deliberate minimal handling: synthesising filler ticks would be inventing market data). Bounded today because nothing in `tracker-flow.yaml` targets a non-AAPL instrument. See also this ledger's `crates/d1/src/lib.rs:771` row, whose justification this change narrowed. (3) **Two `dividend` semantics for one YAML action** — `sim --mode replay` calls `keeper.credit_dividend` and never moves the price; `sim --mode emit-ticks` emits one ex-div `FeedTick` carrying `div_per_share_e9` with all three prices dropped by the dividend. The latter is forced: `run_core` credits dividends from `tick.div_per_share_e9` and nowhere else, so a keeper-credit representation has no transport across a tick file, and `feed.rs`'s M6 remediation already established that crediting cash without dropping the price creates value from nothing. Converging them changes `just sim`'s printed AAPL row from 176.00 to 175.75 — a P1.M5 tracker-output change, ~5 lines, deliberately out of scope here. (4) **`exch_ts_ns` counts from 0** in both producers while `d1-core/src/feed.rs` documents the field as "nanoseconds since Unix epoch" — pre-existing in the synthetic walk too; a doc fix, not a code fix. *Upgrade:* P2.M4 still owns the `expect:` timeline entries, `action: exo_book_event`, and a tracker cadence that samples inside a 9-second scenario. This change covered feed transport only (`quote`/`gap`/`dividend`), by decision.
- **Tick-file values are structurally validated, not plausibility-validated.** `tickfile::parse` enforces shape (exactly six integer fields, non-decreasing `exch_ts_ns`, non-empty) and the `sim` writer uses checked arithmetic throughout (`checked_sub` on the ex-div drop, `checked_mul` on `at_ms → ns`), but nothing rejects a negative price, a crossed book (`bid > ask`), or an implausibly large `div_per_share_e9` — and `d1` credits per-book cash from that last field, so a hand-edited tick file can mint cash. Raised in security review and **deliberately declined**, with the code reviewer independently reaching the same conclusion: a magnitude threshold is a calibrated market convention, which root `CLAUDE.md` requires to live once in `protocol/` reference data rather than hardcoded in a parser, and this ledger's `crates/d1/src/lib.rs:408` row already resolves the identical class ("a business max-transfer-size limit is a Tier-1 risk check, not a code constant"). Bounded today because the only writer is `sim --mode emit-ticks` and `just d1-scenario` regenerates the file into gitignored `delta-one/target/` every run — it is never committed, so it cannot drift or be edited into the repo. *Upgrade:* Tier-1 risk check in `d1.toml` (ADR-008), P4 — same trigger as the `qty_e2` row.
- **Two review findings deferred rather than fixed.** (a) `d1::spawn` now takes **12** positional parameters, three of them adjacent flag-shaped args (`posttrade_cfg: Option<_>`, `deterministic: bool`, `feed_ticks: Option<_>`). Today the `bool` between the two `Option`s pins their positions so all four call sites are compile-checked — the *next* `Option` added will not be. The repo already has the right pattern (`FixConfig`, `PostTradeConfig`, `TrackerConfig`, `StartupOrder`): fold the loose args into a `SpawnConfig` and drop `#[allow(clippy::too_many_arguments)]`. Deferred as out of scope for a transport-only change. (b) `crates/d1/src/lib.rs`'s `next_sample_ns = (tick.exch_ts_ns / sampling_interval_ns + 1) * sampling_interval_ns` is the one `exch_ts_ns`-derived expression in `run_core` that is not `checked_*`, and `--feed-ticks` now sources that field from a file rather than from an internally-generated monotonic clock. Verified **inert**: `run_tick_file_producer` real-time-waits on each tick's deadline before pushing, so a near-`u64::MAX` timestamp is not delivered within any realistic session. Left alone because it sits in `run_core`'s per-tick drain loop. *Upgrade:* (b) becomes reachable the moment a fast-forward or batch replay mode removes the pacer that currently guards it.
