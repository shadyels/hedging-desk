# Roadmap

Scope principle (corrected 2026-07-06): the **instrument universe** starts minimal during development and is enriched at scale in P4.M5 — but **project scope is extensive**. Phases 1–4 are all mandatory and built to the same depth. Each milestone ends demoable.

## Phase 1 — Delta One (Rust) — mandatory

- **P1.M1 — Skeleton & contracts:** compose stack up; protocol codegen; feed ingest from `sim/` replay; position keeper; HDR-histogram bench harness (the latency measurement exists before the features do).
  - Split into two independent slices (ADR-004: Protobuf never enters `d1-core`, so the runtime needs no codegen). **Slice 1 — skeleton runtime** (`d1-core` ids/feed/market-data/keeper modules, `sim` replay mode, criterion+HDR bench): done on `feat/d1-skeleton`. **Slice 2 — contracts** (`gen-proto.sh`, `schema-check.sh`, codegen wired into all three builds; local plugin binaries, ADR-012): done on `feat/d1-skeleton`.
- **P1.M2 — Order path:** order state machine; FIX 4.4 session vs sim acceptor (logon/sequence/resend correct); NewOrderSingle → ExecutionReport round trip; exec reports out on NATS.
  - Split into three dependency-ordered slices. **Slice 1 — order state machine** (`d1-core::order`: `OrderStore`/`Order`/`ExecEvent`/`Fill`, idempotent `apply_exec` via `ExecId` dedupe, unit+proptest coverage, HDR bench): done on `feat/d1-order-state-machine`. **Slice 2 — FIX round trip + threading skeleton** (`d1-gateway-fix` + `quickfix`, `sim` FIX acceptor, `rtrb` SPSC rings core↔gateway per ADR-013, new `d1` binary crate hosting the core thread + FIX gateway, startup synthetic order as the M3 netting-driven-emit stand-in): done on `feat/d1-fix-round-trip`. **Slice 3 — NATS plane + demo** (`d1-gateway-nats` consumes `TargetPosition`, publishes `ExecutionReport`, feed-ingest ring + producer thread, `just demo` wiring): done on `feat/d1-nats-plane`.
- **P1.M3 — Netting & crosses:** multi-book netting per ADR-005; explicit internal-cross booking (netting-generated AND directed-by-instruction, see ADR-009 mechanics note); pro-rata allocations; property tests (Σ book positions == firm position under arbitrary interleavings).
  - Split into three dependency-ordered slices. M2 froze `Order`/`Fill`/`ExecReport` around a single `book_id` and the keeper's universe around the CLI startup order's one (book, instrument) pair, so multi-book netting is a type change and a universe change before it is an algorithm. **Slice 1 — netting engine** (`protocol/refdata/universe.json` loader feeding the keeper/market-data universe at startup; `d1-netting` as a pure engine: per-book demands in, internal crosses + one net external intent out, largest-opposite-first with `book_id` tie-break, no-trade band from `TargetPosition.band_qty_e2` (min over books, gating the external order only); cross-price policy from refdata's `conventions.cross_px_policy_default`, parsed to `RefPxPolicy` and validated at startup as a hard error, ADR-005 §4 forbids hardcoding it (the planned `d1.toml [netting]` section was dropped: root CLAUDE.md defines conventions once in refdata); proptests for cross conservation and `net_external == Σ demands`). No wiring — same shape as M2 slice 1: done on `feat/d1-netting-engine`. **Slice 2 — netting wiring** (netting-cycle trigger + `netting_cycle_id`, in-flight tracking supplying ADR-005's missing `− inflight_b` term, parent external orders spanning books, pro-rata allocation of fills back to books; deletes `target_to_order`; owns the mandatory Σ-book-positions == firm-position proptest under arbitrary fill interleavings): done on `feat/d1-netting-wiring`. **Slice 3 — crosses & directed transfers** (`InternalCrossNotice` out on `d1.crosses`, `InternalTransferRequest` in on `exo.transfers.<book>` through the same booking path per ADR-009's mechanics note; demo: two books with opposite targets → one cross + residual external order): done on `feat/d1-crosses-transfers`.
  - Two constraints worth stating up front: the cross reference price is arrival mid from `crates/d1/src/feed.rs`'s **synthetic** feed (`sim.md.<instrument>` is UI-display-only per `protocol/nats-subjects.md`), and crosses/allocations reach Kafka only in P1.M4 — M3 produces the records, not the topics.
- **P1.M4 — Post-trade:** Kafka/Avro producers for trades, crosses, allocations, order audit; deterministic golden-file e2e test.
  - Split into three dependency-ordered slices. **Slice 1 — encoder engine** (`d1-posttrade` as a pure Avro encoder: `Copy`, id-based ring-payload types — `TradeLeg`/`Cross`/`Allocation`/`OrderAudit`, no instrument symbol/currency string at rest — plus `convert.rs` mapping them to the `posttrade_trade`/`posttrade_cross`/`posttrade_allocation`/`order_audit` Avro schemas via `apache-avro`, resolving symbol/currency from `d1-refdata::Universe` at the edge exactly like `d1-gateway-nats::convert` resolves proto fields; no Kafka, no rdkafka, no threads, no rings — round-trip encode/decode unit tests only): done on `feat/d1-posttrade-encoder`. **Slice 2 — wiring** (`rdkafka` idempotent producer, SPSC ring(s) from the core thread's booking sites (`crates/d1/src/cycle.rs`) into a `d1-posttrade` producer thread, `posttrade.*` topics live, `netting_cycle_id` threaded through from the M3 slice 2/3 booking sites): done on `feat/d1-posttrade-kafka`. **Slice 3 — deterministic golden-file e2e + demo** (fixed clock/uuid seams so `booked_ns`/`ts_ns`/`msg_id` are reproducible in golden output, `just demo` produces and asserts against golden Avro records end to end): done on `feat/d1-deterministic-golden-file`. **Follow-up — Schema Registry framing:** Slices 1–3 published raw Avro datums, leaving ADR-002's Confluent Schema Registry decided but unimplemented (records were undecodable without out-of-band schema knowledge). Closed on `feat/d1-tracker-analytics`: `d1-posttrade::registry` registers the four schemas at producer startup and frames every payload `0x00 || schema_id BE32 || datum`. Golden fixtures unchanged (they store decoded JSON), so they doubled as the regression control.
  - Slice 1 mints `msg_id`/`trade_id`/`allocation_id` (UUIDv7) and `booked_ns`/`ts_ns` (wall clock) inside `convert.rs` at encode time rather than accepting them as params — a deliberate deviation from `d1-gateway-nats::convert`'s pattern (which takes `msg_id`/`sent_ns` in), chosen because Slice 1 has no caller-side clock/uuid seam yet; Slice 3's golden-file determinism needs the mint point to move to an injectable seam, which is that slice's job, not a Slice 1 concern.
- **P1.M5 — Tracker analytics (ADR-010):** per-book cash in the position keeper; sim dividend events; ex-post TE, tracking difference and cash drag in `d1-analytics`; `d1.tracker.<book>` + Kafka daily record.
  - Split into three dependency-ordered slices, Slice 1 deliberately owning **every** `d1-core` change so exactly one slice carries the criterion bench diff the DoD demands. **Slice 1 — inputs: refdata, per-book cash, dividends** (`d1-refdata` parses the three previously-dropped `universe.json` fields into `Universe::tracker_books` + `cash_yield_annual_e9`, failing loud on an unresolvable benchmark symbol, a constituent outside the instrument universe, a benchmark symbol that is not itself quotable, non-positive or duplicate weights, and weights not summing to `1.0e9` — an unenforced weight convention would silently scale the benchmark return and make every published TE a plausible-looking fiction; `PositionKeeper` gains per-**book** `cash_e9`, with `slot()` returning `(book_idx, position_slot)` and `compute_fill()` returning the new *absolute* cash value so `apply_cross` still computes both legs against current state before committing either — the existing `buy_slot == sell_slot` guard then also proves cash-slot disjointness, since the instrument is shared; new `seed_cash`/`cash`/`positions_for_book` (zero-alloc, mirrors `MarketData::iter`)/`credit_dividend` (all-or-nothing via two passes, no allocation)/`accrue_cash`; dividends ride a new `FeedTick.div_per_share_e9` field rather than a ninth ring, which keeps the cash credit and the ex-div price drop deterministically ordered — the second corporate-action type gets its own transport; `sim` finally *acts* on the `action: dividend` timeline entry that had been parsed-and-ignored since M1): done on `feat/d1-tracker-analytics`. **Slice 2 — engine, config, sampling, NATS** (`d1-analytics`, a pure integer-only calculator with exactly one dependency — `d1-core`, for the id newtypes — and no `prost`/`apache-avro`: returns are `_e9`, so squared returns land in `_e18` and `(variance_e18 as u128).isqrt()` yields an `_e9` stdev directly, since `√(x·10¹⁸) = √x·10⁹`, which is how a standard deviation lands on a no-float money path without a third-party crate; sample variance uses the `n − 1` denominator, which is what makes the `n_obs >= 2` publication gate load-bearing rather than arbitrary; annualization is 252 trading days and `sampling_interval_s` deliberately does *not* enter it, so shortening the interval for a test cannot change the metric; every accumulator `i128`/`u128`, narrowing only at the wire edge via `try_from`; `TrackerWindow`'s `VecDeque` pre-allocated once, off the hot path; `d1.toml [tracker]` parsed via the `toml` crate in the new `crates/d1/src/config.rs`, a missing file or section being a hard startup error matching the `cross_px_policy` posture — sampling and window sizes are *operator knobs*, unlike P1.M3's `[netting]` section, which was a market convention and correctly moved to refdata; a ninth `rtrb` ring carries `TrackerRecord` from core to NATS; the sampling driver lives inside the existing `feed_rx.pop()` arm and fires on the synthetic `exch_ts_ns` clock crossing a `sampling_interval_s` boundary, needing no new time seam, and reaching `n_obs >= 2` takes *three* crossings because the first only establishes `prev_nav`/`prev_mid`; cash genuinely accrues the configured yield each sample, without which cash earns 0 in NAV while ADR-010's drag formula assumes otherwise; `TrackerAnalytics` published on `d1.tracker.<book>`): done on `feat/d1-tracker-analytics`. **Slice 3 — Kafka daily record & golden test** (`tracker_analytics.avsc` gains `sampling_interval_s` with a default — BACKWARD-compatible, and the first real schema evolution through `just schema-check`; not cosmetic, since a TE sampled at 60s is not comparable to one sampled daily and the Protobuf already carried the field; `PostTradeEvent::Tracker`, a fifth registered schema, `encode_tracker` resolving `benchmark_symbol` through the existing helper with a checked `u64 → i64` for `as_of_ns`, and the `registry.rs` tripwire that asserted `for_topic("posttrade.tracker.analytics") == None` — written to fail exactly when this milestone landed — duly flipped; the record is emitted **once**, after `run_core`'s drain loop exits, which is both ADR-010 §4's "daily" record read as end-of-session and the reason the four existing golden fixtures stay byte-identical: `rtrb` is FIFO and the ordered-shutdown contract joins `core` before signalling the producer, so that push is provably both last-in-stream and still drained, whereas a mid-stream insert would shift every `msg_id` in the `Stamper::Fixed` sequence; the golden test therefore gains **no fifth fixture** — `n_obs` depends on real handshake timing, so a byte-diff would be permanently flaky — and instead asserts one record by property, synchronising on a bounded poll of `d1.tracker.1` rather than a wall-clock floor): done on `feat/d1-tracker-analytics`. **Follow-up — review remediation:** four of six code-review MEDIUMs were comments or assertions claiming behaviour the code did not have — a guard aimed at a field that could never take the bad value, contradictory docs about an unconditional refresh, overflow bounds understated by ~20 orders of magnitude, and a doc promising an ex-div price move that did not exist (now implemented, so the demo no longer creates value from nothing).
- **Exit:** `just demo` runs the tracker-flow scenario end to end (incl. tracker analytics); bench report p50/p99 within budget on release build.
  - **Not yet met as of P1.M5, and not P1.M5's to meet.** Tracker analytics *are* exercised end to end by `just demo` against real NATS/Kafka/Schema-Registry, but the tracker-flow **scenario** is not: `sim/src/replay.rs` is standalone and never feeds the `d1` process, and the scenario's `exo_book_event` / `expect: exo_targets_republished` entries need EXO. This clause therefore contradicts **P2.M4**, which already owns "Full tracker-flow demo storyline runs" — a document contradiction to resolve, not an implementation gap. The second conjunct is also outstanding: a criterion micro-bench on `apply_fill` is not a tick-to-trade p50/p99 report.

## Phase 2 — EXO (Python) — mandatory

- **P2.M1 — Engine + first products:** Heston MC engine (scheme chosen via convergence test) with QMC (Sobol + Brownian bridge) and variance reduction (antithetics baseline, control variates where a closed form exists); barrier option + autocallable; validation gates green (BS-degenerate closed forms, Heston vanilla characteristic function).
- **P2.M2 — Equity product set:** reverse convertible, barrier reverse convertible, bonus certificate (payoff layer only).
- **P2.M3 — FX products:** TARF, PTARF under Heston-FX (two rates); illustrative parameter set, calibration caveat documented until P4.M4.
- **P2.M4 — The loop:** portfolio deltas per book, rehedge banding, target publication, fill consumption, reconciliation halt behavior; Tier-1 Greek limits + `d1.alerts.limits` alerting (ADR-008). Full tracker-flow demo storyline (ARCHITECTURE.md) runs.

## Phase 3 — UI (TypeScript) — mandatory

- **P3.M1 — Monitoring:** desk risk board with the full monitored Greek set (delta/gamma/vega/rho/theta/div-sens + limit states) and tracker scorecard (TE / tracking difference / cash drag, ADR-010), blotter with crosses as first-class rows, system health incl. valuation metadata.
- **P3.M2 — Actions:** manual ticket + kill switch + hedge-proposal approve/reject over `d1.cmd.*` request/reply; rejection paths rendered properly.

## Phase 4 — Advanced hedging & enrichment — MANDATORY, same depth as 1–3

- **P4.M1 — Rates foundation:** rate instruments + DV01/tenor conventions in refdata (replacing DEMO placeholders with a documented convention set); EXO rates mapping (rho per ccy bucket → futures-equivalent quantities).
- **P4.M2 — Rho transfer:** directed internal cross EXO-SP → RATES-IR (`exo.transfers.*`, ADR-009); RATES-IR external futures hedge generated through the ordinary target pipeline; golden-file scenario.
- **P4.M3 — Hedge proposal engine (full optimizer, ADR-009):** vega/liquidity QP over the listed option chain; `HedgeProposal` bus flow; D1 proposal cache, validation, execution; UI approve/reject; property test — recomputed post-exposure from proposal legs matches the claim within MC error.
- **P4.M4 — Model depth:** Heston-local-vol leverage surface; PDE pricer as MC cross-check for single-asset barriers; calibration framework calibrating Heston(-LV) to **sim-generated synthetic vanilla surfaces** (framework is real and demoable; swapping in live market quotes is a Phase 5 data change, not a code change).
- **P4.M5 — Multi-asset:** worst-of autocallables/BRCs on 2–3 correlated underlyings (correlated Heston, LSV extension where calibrated); payoff layer reuses the P2 abstraction; correlation is a documented demo parameter until Phase 5 market calibration.
- **P4.M6 — Universe enrichment at scale:** the "go big" step — broad multi-asset instrument sets, full option chains per underlying, additional FX pairs and bonds; `advanced-hedging` extended demo scenario runs end to end (breach → proposal → approval → options execution → booked; rho → transfer → external futures hedge).

## Phase 5 — Optional / externally gated

- Proprietary venue FIX dialects (EMSX, TSOX, FXAll — need specs and entitlements); calibration against live market data feeds;
- JetStream evaluation for replayable target history; 
- **AI assistance (ADR-011)**: an LLM decision-support layer (risk Q&A, morning briefing, proposal narration, scenario authoring — read-only, non-executing) and an ML research track (deep hedging for the rehedge policy, ex-ante TE, NN-accelerated calibration — shadow mode first); 
- rough-volatility models (rBergomi) — research-strong on short-dated skew but not established desk practice for exotics pricing, so optional by the project's own tech rule.
